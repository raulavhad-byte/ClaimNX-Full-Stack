## Objective

Review the approved Insurance Foundation physical design for PostgreSQL correctness, migration order, compatibility, data remediation, tenant isolation, audit integrity, and safe forward-only evolution.

## Review Decision

**Result: approved design candidate for forward-only migration, subject to this review's approval.**

The existing `public.insurance_entities` table has one Blue Cross record and is referenced by one Claim through `claims.payer_id`. It must be evolved in place. The table and its existing primary-key UUID must not be dropped, renamed, or replaced.

## Required Migration Order

| Order | Migration responsibility | Why this order is required |
| --- | --- | --- |
| 1 | Read-only/guarded preflight validation | Stops the migration if the legacy table, Claim foreign key, or prerequisite foundations differ from the reviewed evidence. |
| 2 | Reference Data validation/seed | Partner, contact, plan, and enablement classifications must exist before valid rows can be backfilled or constrained. |
| 3 | Additive evolution of `insurance_entities` | New columns begin nullable/defaulted so the existing Blue Cross record can be mapped safely. |
| 4 | Deterministic audit and controlled-value remediation | Backfill Partner Code, display name, type/status references, audit fields, deletion flag, and version. |
| 5 | Root constraints, foreign keys, and active uniqueness indexes | Applied only after every legacy record satisfies Phase 7 requirements. |
| 6 | Create Contact, Product/Plan, and Enablement tables | New aggregates depend on the final Partner root and external foundations. |
| 7 | Create indexes and compatibility comments | Completes lookup performance and documents legacy-write restrictions. |
| 8 | Create transactional command functions | Functions depend on final schema constraints and are the database write boundary. |
| 9 | Post-migration validation | Proves claims compatibility, audit readiness, referential integrity, lifecycle rules, and index presence. |

## `insurance_entities` Compatibility Review

- Preserve the table name, `id`, and the existing `claims.payer_id` foreign-key target.
- Do not change the identity of the Blue Cross record (`d4bbf5b8-c22b-4d2e-8e94-352750d680e5`).
- Preserve every legacy column and existing check constraint until the associated legacy API is explicitly retired.
- Add Phase 7 columns; do not repurpose the legacy `type`, `name`, `email_id`, or `data` columns as authoritative new-write fields.
- New command functions treat `partner_code`, `display_name`, reference-value IDs, audit columns, `deleted_at`, `is_deleted`, and `version` as authoritative.
- The legacy primary-key default is a compatibility concern. The migration must inspect it and document its handling; new Phase 7 command functions always accept application-generated UUIDs and never rely on a database-generated business ID.
- Hard deletion is prohibited because claims retain historical payer references.

## Remediation Requirements

Before adding `NOT NULL` constraints to the evolved root, the migration must supply one valid existing `public.users(id)` actor and:

| Legacy source | Target field | Required mapping |
| --- | --- | --- |
| `name` (`Blue Cross`) | `display_name` | Trimmed legacy name. |
| Generated reviewed value | `partner_code` | Stable, unique code such as `BLUE_CROSS`; do not derive it at run time without a reviewed mapping. |
| `type` (`Insurer`) | `partner_type_reference_value_id` | Active `INSURANCE_PARTNER_TYPE / INSURER` Reference Value. |
| Approved initial state | `operational_status_reference_value_id` | Active `INSURANCE_PARTNER_STATUS / ACTIVE` Reference Value. |
| Existing timestamps | `created_at`, `updated_at` | Retain existing timestamps where valid. |
| Migration actor | `created_by`, `updated_by` | Existing IAM User ID. |
| Legacy active row | `is_deleted`, `version` | `FALSE`, `1`. |

The migration must fail atomically if any required mapping is missing or if the legacy root contains unexpected unmapped rows.

## New Table Review

### `insurance_partner_contact`

- Independent UUID child identity is generated by the application.
- `insurance_partner_id` uses `RESTRICT` foreign key to the evolved root.
- A partial unique index enforces one active primary Contact per Partner/Contact Type.
- Contact writes are made through the Partner aggregate command boundary and increment the parent Partner version.

### `insurance_product_plan`

- Independent aggregate UUID, Partner-owned by reference only.
- Partial active uniqueness on Partner + Code and Partner + normalized Name.
- Activating a Plan verifies that its Partner is active through command/application validation.
- No policy, benefit, eligibility, or claim fields are included.

### `organization_insurance_partner_enablement`

- Holds the only tenant-scoped Partner relationship.
- Partial active uniqueness on `(organization_id, insurance_partner_id)` prevents duplicate tenant enablements.
- Every mutable command requires and filters by `organization_id`; a caller cannot trust client filtering.
- The table does not copy Partner master data and cannot alter it.

## Reference Data Dependency Review

The structural migration must validate—not invent—these categories and approved values before writes:

| Category | Required values |
| --- | --- |
| `INSURANCE_PARTNER_TYPE` | `INSURER`, `TPA` |
| `INSURANCE_PARTNER_STATUS` | `DRAFT`, `ACTIVE`, `SUSPENDED` |
| `INSURANCE_CONTACT_TYPE` | At least `OPERATIONAL`, `BILLING`, `ESCALATION`, `INTEGRATION` |
| `INSURANCE_PLAN_STATUS` | `DRAFT`, `ACTIVE`, `INACTIVE` |
| `ORGANIZATION_PARTNER_ENABLEMENT_STATUS` | `ACTIVE`, `SUSPENDED` |

Foreign keys guarantee a valid Reference Value exists. Command functions additionally validate that the value belongs to the approved category and is active/non-deleted.

## Constraint and Index Review

| Concern | Database control |
| --- | --- |
| Existing Claim payer integrity | Retain `claims.payer_id -> insurance_entities.id`; all root deletes are restricted/soft only. |
| Duplicate active Partner code/name | Partial unique indexes over non-deleted root records. |
| Duplicate primary Contact | Partial unique index filtered by `is_primary = TRUE` and active row. |
| Duplicate Partner Plans | Partial unique indexes per Partner Code/normalized Name. |
| Duplicate tenant enablement | Partial unique index for active Organization/Partner pair. |
| Invalid audit history | User `RESTRICT` foreign keys; required audit actors/timestamps. |
| Stale writes | Expected-version predicate and version increment in every mutable command. |
| Soft-delete inconsistency | Check constraint joins `deleted_at` and legacy-compatible `is_deleted` where present. |
| Tenant escape | Enablement command filters on requested Organization ID and verifies active membership/permission in application/API layers. |

## Transaction and Rollback Position

- Each migration runs in a transaction and fails atomically.
- No destructive rollback migration is provided. Corrections are new, reviewed, forward-only migrations.
- No `DROP TABLE`, `DROP COLUMN`, `RENAME TABLE`, or Claim foreign-key replacement is permitted.
- The mandatory post-migration validation must verify that the Blue Cross UUID still exists and that the Claim payer foreign key is unchanged.

## SQL Command Boundary (Later Step)

After the structural migrations are approved and validated, SQL command functions will be created in this order:

1. Partner create/update/activate/suspend/retire and Contact child commands.

4. Tenant-scoped reads and effective availability queries.

No REST API, NestJS code, or write function is created by this review.
